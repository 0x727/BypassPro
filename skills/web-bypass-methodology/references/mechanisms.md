# 从第一性原理推导绕过实验

用途：从边界目标、输入表示、转换、决策与实际使用关系生成新技术。产品名、CVE、编码名和历史 payload 提供实例；推导可以直接从现场和底层操作出发，不受实例目录限制。

模型未知不妨碍研究。只补全当前候选需要的局部关系，其他节点标为未知，持续用实际请求获取证据。深入分析与多轮执行相互推进，不要求先猜清整个服务端。

## 先定义要保持的安全关系

用现场明确：实际身份、资源/动作、所属租户、入口、输入语义和有关状态，按什么策略应当被允许或拒绝。WAF 测试还要明确要确认的是检测边界、到达业务层，还是进一步业务影响。

把“检查层认为是什么”与“最终使用的是什么”分开。值得研究的失配包括：表示不同、检查和使用对象不同、信任来源不同、检查遗漏，以及检查后状态改变。解析差异不是全部解释；完全一致的解析也可能遇到错误授权或来源信任。

同一资源的别名、等价字符串或另一入口是否应执行相同策略，由目标契约决定。原始字节签名、格式限制和正常认证条件可能有意区分表示；不能由业务值相同直接断言安全检查必须放行。

## 把相关节点写成输入与输出契约

对有关系的节点按需记录，证据不足的格子留为假设：

| 契约部分 | 要问的底层问题 |
| --- | --- |
| 输入对象 | 收到原始字节、UTF-16 code unit、Unicode 字符、字符串、字段集合、AST、路径还是资源标识？ |
| 来源与上下文 | 从连接、代理、头部、会话、配置还是业务字段取得？谁能控制或覆盖？ |
| 操作 | 解码、拆分、合并、归一化、查表、缩窄、类型转换、名称解析、授权或状态更新？ |
| 范围 | 整个实体、某字段、重复项中的某一项、某段、前缀、指定长度，还是错误前的局部输入？ |
| 分支 | 怎样选 parser？成功、非法、缺失、超长、未知声明时分别继续什么路径？ |
| 输出与使用 | 产生什么对象，由谁继续读取？检查结果绑定了哪个身份、资源、动作与状态？ |

画相关片段即可，例如：`输入字节 → 选择解码器 → 字段解析 → 检查 → 后续转换 → 使用`。节点顺序由目标证据决定；缓存、转发、别名和状态变化可以使它成为分支或图，而非固定流水线。

## 从底层操作发散技术

以下是生成问题的算子，不是必测目录。对实际存在或尚未验证的操作，寻找不同输入、边界条件、作用位置与组合，再建立能观察结果的请求：

| 操作类别 | 可以派生的问题与技术方向 |
| --- | --- |
| 解码/展开 | 输入是否经字符集、percent、escape、Base64、压缩等转换？检查前后、层数、连续片段和入口是否一致？ |
| 归一化/丢弃 | 大小写、点段、全角、空白、未知字段或分隔是否被折叠、清洗或忽略？哪些不同输入得到同一结果？ |
| 拆分/合并 | 在解码前还是后识别分隔符？重复值、数组、对象、字段片段怎样选取或组合？ |
| 缩窄/查表 | 字符写为字节、位掩码、符号转换、hex 索引如何处理高位、非法值和未填充表项？ |
| 类型转换 | 字符串/数值、布尔、空值、缺失、数组/标量如何处理？精度、范围和转换失败怎样影响后续比较？ |
| 选择实现 | 媒体类型、charset、BOM、输入 API、路由或配置是否选择不同 parser 和校验路径？ |
| 投影/检查范围 | 检查层看哪些字段、位置、重复项或长度，业务层又消费哪些？是否检查了最终组合后的对象？ |
| 异常/默认/回退 | 非法、未知、过大或部分解析后是拒绝、截断、忽略、换 parser、套默认值还是继续处理？ |
| 名称解析 | 域名、SNI、Host、原始/规范化路径、路由别名与最终资源是否指向同一对象、应用同一策略？ |
| 身份/信任重建 | 哪一层把凭据、连接或客户端可控元数据认作身份/来源？后续是否覆盖或重新构造？ |
| 状态/复用 | 检查与使用是否依赖同一状态版本？缓存键、会话、重试、一次性值和跨请求复用如何绑定上下文？ |

需要具体编码和 parser 入口时读取 [编码与解析器技术](encoding-and-parsers.md)；需要路径、方法、头部等实例时读取 [绕过技巧库](bypass-techniques.md)。没有命名的操作或新关系可以直接加入模型。

## 反推同一业务结果的不同表示

设 `T` 是相关转换，`y` 是要保持的受控结果。把候选理解为 `E(y) = {x | T(x) = y}`：从结果反推可能到达它的多个输入。这个集合是研究工具，目标是否执行 `T` 仍需验证。

| 受控结果或操作 | 可以怎样展开候选 |
| --- | --- |
| percent decode 得到 `A` | 比较原字符、`%41`、相关 hex 表示和有依据的嵌套；在不同入口确认真实还原 |
| 某步字符缩窄得到 `A` | 对 `g & 0xff == 0x41` 生成不同高位字符；再核对传输、字符读取和缩窄范围 |
| parser 读取某个受控字段 | 比较原字段、合法转义、不同承载位置、重复/结构表示，确认最终消费的值及类型 |
| 路由到同一受控资源 | 从已有别名、段和路径表示反推候选，核对实际资源与策略，而非只看字符串相似 |

局部等价不意味着完整请求等价。身份、资源、动作、状态和上下文中需要保持的因素也要比较。不同表示被安全层不同处理只是线索；原受限语义恢复与边界证据才能支持相应结论。

反过来，保留检查层看来相同、业务层却可能不同的候选，例如重复字段取值、检查范围外的受控值或后续组合。两种推导方向都可以进入多轮队列，不用模型置信度提前淘汰未知关系。

## 转换次序、层数与触发分支

比较检查和业务处理的顺序。若相关操作 `F`、`G` 的输入类型和前提都满足，研究 `F(G(x))` 与 `G(F(x))` 是否产生不同结果；不能机械调换不能接受同类输入的操作。

- **拆分与解码**：`A%26B` 是分割前可被解码成含 `&` 的字符串，还是被分割后作为一个值解码？跟踪原参数与实际字段集合。
- **检查与后续解码**：`%2541 → %41 → A` 的各步发生在哪里？是否有检查只看中间态？更深表示需要相应真实处理，不靠编码层数断言效果。
- **归一化与检查**：如果后续仍会改变决策对象，检查绑定的是否是最终对象？一次清洗和重复清洗可能有不同结果，但差异本身不证明边界失败。
- **嵌套上下文**：正文解码、JSON 字符串还原、业务 URL 解码等是否分别处理实体、字段或局部片段？外层和内层不能随意互换。
- **触发与范围**：合法转义、BOM、某字段、输入 API 或错误处理是否触发另一条分支？改变有/无触发、位置和作用范围，而非固定某个“魔法字符”。

可检查重复处理是否仍改变结果，例如 `F(F(x))` 与 `F(x)`。是否应该幂等由该操作契约决定；正常的分层解码也可能非幂等，只有检查与使用的实际关系才能决定安全影响 [P1–P2]。

组合可以直接测试，不要求单项先命中。记录必要中间态与未知箭头，命中后用移除、交换、换组或替换触发点的对照解释其作用；未命中保留实际条件与其他组合机会。

## 类型、位宽、单位与边界

编码案例应继续下探到实现：读入的是字符还是字节、是否经过有损转换、索引是否被掩码、返回值怎样传给下一步。不要把同一个字面的“长度”当作同一量。

| 可能的失配 | 需要比较的量或行为 |
| --- | --- |
| 字节/字符/code unit | UTF-8 字节长度、Unicode 字符、UTF-16 code unit 与读取范围；非 BMP 字符不能直接套单个 char 的模型 |
| 字符缩窄/数值解析 | 低 8/7 位、符号及查表索引，与 `Character.digit` 等数字属性分别验证 |
| 字符串/数值 | 原词法表示、前导字符、范围、精度及实际数值；字符串 `"01"` 与数值 `1` 不能先假定业务等价 |
| 单值/集合 | 重复项的 first/last/list、数组/标量、拼接和展开，记录顺序与最终类型 |
| 空/缺失/默认 | 空字符串、null、缺失字段、默认值和转换失败是否走不同路径 |
| 长度与位置边界 | 检查和使用的长度单位、前缀/完整内容、错误前已读内容、解压前后范围 |

围绕可控边界选择相邻条件，并保持其他语义；不采用所有 WAF 共用的长度阈值。范围、类型、精度差异都是候选，只有具体入口与业务行为才能确认其含义 [P3]。

## 异常、默认与局部检查

为候选同时考虑成功、非法、缺失、未知声明和大小边界，而不是只考虑正常解析路径。检查层和业务层可能在不同条件下选择解析、默认或回退，先辨别真实行为。

使用受控字段和标记比较：原合法输入、局部改变后的输入、必要对照及实际业务结果。若想研究部分检查，保持业务确实消费的字段，追踪检查选择的范围和最终消费范围；格式错误导致字段丢失不能证明原语义通过。

区分“拒绝整个请求”“仅不匹配某条规则”“当普通字符串检查”“部分解析”“切换业务 parser”。规则不匹配也不意味着整个 WAF 放行。AWS WAF JSON 的公开配置展示了不同失败和过大组件策略，但当前目标选择哪条分支仍需证据，不由产品名字确定 [P4]。

新错误页、415、EOF 或耗时变化用于生成后续条件与对照，不能单独确认内部实现。观测不足保留未判定，继续实际探索；工具侧截断与目标侧截断也要分开。

## 名称、实际对象与信任绑定

向前追踪“该名称怎么被解释”，再从最终资源向后追踪“哪一步检查了它”。域名/IP、SNI/Host、原始/规范化路径、别名、内部转发和实际对象标识分别记录；同一名称字符串也可能在不同上下文解析为不同对象。

从来源追踪身份或元数据：谁建立、谁覆盖、谁验证、谁采信，后续是否再次改变。对代理头、身份字段或资源参数，保存真实连接与测试会话，用单项或有依据的组合检查最终决策。客户端声明不改变真实 TCP 来源 [P5]。

对凭据、签名或认证材料，核对其绑定的是哪种表示及哪些上下文；仅有字符串差异、正常认证成功或签名失败，不能证明绕过。访问控制结论依赖同一受限身份取得应拒绝的业务结果。

对入口名称与连接映射读取 [连接、域名与入口](connection-routing.md)，避免把换到默认站点当作访问了原受限资源。反推得到的新候选仍遵守当前目标范围，不自动扩展到关联资产。

## 状态、缓存与检查时点

同一字节请求重复后结果不同，可以来自会话、一次性材料、缓存、资源版本、重试或并发状态。把状态加入条件，而不是要求所有差异都由编码解释。

检查与使用是否绑定同一资源和状态版本，是否有后续变化使先前判断失效，是一种独立候选关系 [P6]。对任务允许的受控状态，可比较状态变化前后及基线；涉及同步、并发或写操作时按任务允许的动作研究，不用增加流量替代机制证据。

缓存研究分别记录键、内容来源、身份/租户及资源条件，核对不同请求是否复用了本不应共享的结果。公开缓存、正常 304 或缓存旧内容可能解释变化，不能直接当成权限失败 [P7]。

使用交错基线、候选复发和各次快照观察稳定性。保存命中与未命中、数量和状态；重复请求用于检验条件依赖，重复模型意见不提高证据等级。

## 从源码和现场继续下探

有源码时，追踪实际调用与数据类型，不只寻找库名：输入来自 byte 还是 Reader，转换是否丢失高位，hex 是否先校验再查表，重复项和错误怎样处理，分支是否处理整个字段，以及返回值之后又进入哪些操作。项目 parser 预览只证明本地模型，不证明目标使用同一入口。

黑盒时从完整回包、受控业务标记、正常/拒绝/局部变化对照和可获得的日志推断局部关系。未知节点留为假设，不要求先有产品指纹或后端源码。实际发送器也在链路里：核查重编码、规范化、长度重建、协议、目标和跳转；Raw 仍经过网络与中间组件。

持续探索时从相同原始证据重新出发，可轮换以下观察角度：由最终使用反推输入、由检查范围反推遗漏、由错误分支反推接收条件、由类型和单位反推边界、由状态变化反推复用关系。角度随问题选择，不固定角色、轮数或阶段。

每个派生想法接回 [候选状态与持续派发](experiments.md#候选状态与持续派发)：作用位置、要保持的语义、未知操作、预期观测、真实发送与对照。新机制、新表示、组合和原请求复验都能继续推进；不要求新增技术名才允许下一轮。

模型生成的复杂链条只是一组可验证假设。优先减少没有依据的额外箭头，但不能因解释简单、思路趋同或几次失败而缩减用户要求的覆盖与复验。按目标证据和现有停止规则结束相应工作，不能用“底层已经推理完了”替代它们。
